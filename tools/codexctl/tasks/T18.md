## 目标

给 `Door` 加一个开关：勾上之后，这扇门在猎杀期间会自动关上并锁死，
猎杀结束后解锁。

这是设计上定死的一条——**鬼只在二楼，一楼是基地；猎杀一开始，
通往一楼的门就锁住**，玩家不能靠冲下楼梯白嫖安全区。

## 要改两个文件

1. `Assets/_Project/Scripts/World/PlayerInteractor.cs` —— 修一处契约不符
2. `Assets/_Project/Scripts/World/Door.cs` —— 加猎杀上锁

## 现状（先读明白再动手）

- `Door` 实现 `IInteractable`，现在 `CanInteract` 恒为 `true`
- `PromptText` 按 `IsOpen` 在「[E] 开门 / [E] 关门」之间切换
- `UpdateNavMeshObstacle()` 在开关状态变化时把 `NavMeshObstacle.carving`
  设成 `!IsOpen`——**门关上就会 carve 掉导航网格**
- `GhostAI` 开门前会检查 `interactable.CanInteract`
  （`GhostAI.cs:724` 与 `GhostAI.cs:1168` 两处）

所以「`CanInteract` 置 false + 强制关门」这一个动作，同时就挡住了玩家、
挡住了鬼开门、也挡住了鬼从门洞寻路穿过去。**不要另外再写阻挡逻辑。**

## 一、先修 PlayerInteractor 的契约不符

`IInteractable` 的契约注释写的是：

> `CanInteract` —— 当前是否可交互。为 false 时按 E 无反应。
> `PromptText` —— 返回 null 表示不显示提示。

也就是**「能不能交互」和「显不显示提示」是两件事**，分别由两个成员决定。

但 `PlayerInteractor.cs:128-131` 现在是这样：

```csharp
IInteractable nextInteractable = IsInteractableAlive(_cachedInteractable)
    && _cachedInteractable.CanInteract
    ? _cachedInteractable
    : null;
```

`CanInteract` 为 false 就把目标整个丢掉，提示也一起没了。结果是玩家瞄准
一扇锁住的门时**什么都看不到**，和瞄准一面墙没有任何区别——他会以为是 bug。

**改法**：`SetCurrentInteractable` 照常收下这个目标（于是 `PromptText`
照常广播出去），但按 E 时不执行。`HandleInteractPerformed` 里
（`PlayerInteractor.cs:140`）已经有 `!_currentInteractable.CanInteract`
的判断，那一处**保持不动**，它本来就是对的。

只把上面那段三元表达式里的 `&& _cachedInteractable.CanInteract` 去掉。

**注意**：`HandleInteractPerformed` 在 `CanInteract` 为 false 时会调
`SetCurrentInteractable(null)`，那会把提示清掉。改成直接 `return`，
不要清空当前目标——否则玩家按一次 E 提示就消失了。

除这两处外，`PlayerInteractor` 的其它任何一行都不许改。

### 这个改动的连带影响，确认过是可接受的

- `GhostWritingBook.CanInteract => IsPlaced`。未放置时书在玩家手上，
  射线打不到，所以不会显示多余提示
- 准星会在锁住的门上照常高亮。这是已知的取舍：高亮和提示文本共用
  `OnInteractPromptChanged` 一个字符串，要分开就得加新事件，不值得

## 二、Door 加猎杀上锁

```csharp
[Tooltip("勾上后，这扇门在猎杀期间会自动关闭并锁死。只给通往一楼的楼梯门勾")]
[SerializeField] private bool _locksDuringHunt = false;

[Tooltip("上锁时玩家看到的提示文本")]
[SerializeField] private string _lockedPromptText = "门被什么东西抵住了";
```

行为：

1. `OnEnable` 订阅 `GameEvents.OnHuntStart` 与 `GameEvents.OnHuntEnd`，
   `OnDisable` 取消订阅。**两个都要，别只订一个。**
2. `OnHuntStart` 时，若 `_locksDuringHunt` 为真：先走**现有的关门流程**
   （复用已有的开关门方法，让它照常播动画、照常更新 NavMeshObstacle），
   再把内部的 `_isLocked` 置真
3. `OnHuntEnd` 时把 `_isLocked` 置假。**不要自动重新开门**，
   保持关着，让玩家自己推开
4. `CanInteract` 改成 `!_isLocked`
5. `_isLocked` 为真时 `PromptText` 返回 `_lockedPromptText`
6. `GameEvents.OnRoundStart` 也要订阅：回合开始时无条件解锁，
   否则上一局猎杀中途结束会把锁状态带进下一局

`_locksDuringHunt` 为 false 的门（场景里绝大多数）行为必须和现在**一模一样**，
不允许有任何可观察的差别。

## 一个已知风险，不要试图在本任务里解决

如果猎杀开始的瞬间鬼正好站在这扇门的门洞里，强制关门会在鬼脚下 carve 掉
导航网格，鬼可能被挤出 NavMesh。`GhostAI` 已经有 `isOnNavMesh` 保护，
不至于报错。**本任务不处理这个，也不要去改 `GhostAI`。**
把这条写进你的最终回复里作为已知限制。

## 验收标准

Henry 在 Unity 里点：

1. 编译通过，`git diff` 只有 `Door.cs` 与 `PlayerInteractor.cs` 两个文件
2. 场景里任意一扇**没勾** `_locksDuringHunt` 的门，猎杀期间照常能开能关，

7. 猎杀中途按 F10 结束回合、再开新一局，楼梯门是解锁状态
